# ADR 0004 服务端统一管理工具路径

日期为 2026-11-10。状态为用户明确要求，M1 检查边界已修正，服务端与管理页面纳入 M2。

## 背景与偏差来源

用户明确希望先提供候选工具列表，再由服务端统一维护工具路径。原始 M1 任务要求采集竞赛开发工具信息，开发实现将这一要求自行具体化为 PATH 和常见安装目录搜索。该实现选择随后写入采集文档，测试围绕自动发现行为展开。脚本化调整时又扩展了文件后缀搜索，延续了同一假设。

偏差产生于工具选择、路径配置、机器状态检查三项责任未被明确拆开。以只读方式访问文件解决了系统副作用问题，工具路径的决定权仍需独立落实到服务端。

## 决定

- 项目提供候选工具清单，包含稳定 ID、显示名和种类，路径初始为 null。管理端允许选择清单中的工具或添加自定义工具。
- 工具的使用范围、实际客户端路径和配置版本由服务端维护。下发给每台机器的是已经确定的有效配置快照。
- 客户端逐项读取配置中的完整文件路径，核对文件存在性，按种类读取 PE 文件版本或标记脚本版本资源不适用。
- 缺少配置时报告 `not_configured`。配置路径不存在时报告 `missing`。权限不足和指向目录等非文件对象分别报告，管理员根据检查结果更新配置。
- 每份检查报告携带所使用的配置版本。服务端按版本关联结果，历史报告作为对应配置或旧采集方式的证据保存。

## 当前落地

M1 采集器 0.1.2 通过 `--tools-config` 读取版本化 JSON，`--list-tools` 输出候选清单。检查输入由配置中的 ID、name、kind 和 path 构成。默认采集的工具状态为未配置。此前的 `--tool-dir` 参数已退出当前接口，调用方应迁移到完整路径配置。

实现已移除 PATH / 常见目录搜索及后缀枚举。报告 Schema 3 使用配置版本和逐项检查结果，读取模型保留 Schema 1 / 2 历史报告的解释能力。示例清单位于 [tool-catalog.json](../../config/tool-catalog.json)，用法见 [采集说明](../inventory.md)。

## 后续交付与验证

服务端和 Web 管理工程尚待 M2 建立。工具配置切片需交付页面、API、鉴权、持久化、下发和结果反馈，支持管理员维护目标机器的有效配置。脚本包及解释器的运行验证按 M3 继续实施。

回归测试覆盖未配置时零工具文件访问、仅访问配置路径、同名 PATH 文件存在时仍报告配置路径缺失、目录和权限错误、错误配置在检查前拒绝、自定义文件名和脚本种类、配置版本回传与历史报告读取。配置来源、目标选择和执行边界同时进入需求与代码自审。
