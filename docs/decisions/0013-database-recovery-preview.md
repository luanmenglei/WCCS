# ADR 0013 数据库连接恢复与等待预览隔离

日期为 2026-11-12，状态为已实现。关联 [项目审查](../tasks/xcpc-waiting-review.md) 与 [修复验证](../tasks/database-recovery-preview.md)。

## 背景

服务端原先持续复用启动时建立的 PostgreSQL Client，连接驱动退出后无法恢复。等待控制预览还与设备续租共用连接互斥锁和 `configuration_head FOR UPDATE` 栅栏，逐座位读取最多产生 2006 条计划查询。

现有写事务依赖栅栏串行化权限修改、版本核对、请求去重和设备控制。本次继续使用固定版本的 tokio-postgres，增加连接生命周期管理及预览专用连接。

## 决定

- 每个应用实例保留一条串行业务连接，并按需创建一条等待预览连接。两条连接使用相同的完整数据库配置，包括数据库、身份、search_path 与 statement_timeout。
- 获取连接时检测 Client 是否关闭，在该连接的互斥锁内建立替代连接。同一连接同时只有一次重连尝试，整个连接握手限时三秒，失败后冷却一秒。取消中的尝试也保留冷却时间。
- TCP keepalive 空闲五秒、间隔一秒、最多三次探测，支持 TCP_USER_TIMEOUT 的平台使用八秒。实际断线检测受操作系统及网络条件影响，Linux 静默丢包计时需部署验证。
- 重连只恢复连接。数据库迁移、启动时取消旧命令和重置在线状态仍由应用启动入口执行。应用内登录会话和 server_epoch 持续有效。
- 连接建立失败、已关闭连接和 PostgreSQL 连接类错误返回 503。业务事务失败交回调用者，以原 request_id 重试时进入已有持久去重逻辑。提交结果不确定时也通过该逻辑核对。
- 等待预览使用专用连接上的 `REPEATABLE READ READ ONLY` 事务，从同一快照读取账号权限、机房范围、身份和设备状态。此入口使用无写栅栏的共享鉴权实现。预览提交时仍通过业务连接取得写栅栏，重新检查当前权限、范围、版本和 preview_token。
- `waiting::plan` 将选手、设备版本、最近命令和控制状态改为集合查询，按输入座位顺序生成结果。计划内部固定十条查询，鉴权和事务命令另计。进入、结束、准备登录及恢复教学共用该实现。

## 影响

每个实例最多增加一条数据库连接。预览之间仍串行，现有写操作与设备续租仍保留统一顺序。慢预览可以与续租并发，业务提交仍可能因目标或权限更新而要求重新预览。

每条连接分别维护重试状态。数据库短暂不可用期间页面显示可重试的存储连接错误，客户端继续按照已有失联及租约规则恢复。连接恢复后的控制请求继续核验设备凭据、身份代次、实例、会话及命令授权。

## 重新评估条件

在目标 Linux 服务器上完成 200～300 台控制连接、500 座位预览、批量提交及静默丢包的并发测量。若写入串行化影响续租时限，再调整写事务粒度或连接池，并补充权限变更、去重和控制命令竞态证明。
