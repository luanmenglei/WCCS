# 设备控制与座位图性能评估

## 测量条件

基线为 `8926b47`。开发机为 Windows 11 x64（10.0.26300），Ryzen 9 8945HX，32 个逻辑处理器，约 31.3 GiB 内存。服务端和模拟设备使用 Rust 1.99.1 的 release 构建，在同一测试进程内通过回环 WebSocket 通信。管理端使用 HTTP，独立的回环 PostgreSQL 18.4 实例开启了 `pg_stat_statements.track_planning`。每轮创建新的 schema，预置 500 个座位、选手和已注册设备。

每台设备建立独立的认证连接，在收到回复后等待一秒，再发起下一次交换。管理员批量提交进入等待、重放同一请求，并在持续负载中反复请求等待列表、管理快照和目标预览。管理循环检查前两个接口的 HTTP 状态，并读取、解析预览响应。模拟器在授权有效期间重复附带完成回执。用例核对逐机结果、审计记录和重连后的授权。命令接收延迟从发起首次提交计时，包含服务端提交、排队和等到设备下一轮心跳的时间。上线计时截至所有模拟设备完成首次交换。

## 优化前后

设备每次续租都要核对操作员权限、设备身份和座位分配。基线在每次 PostgreSQL 事务中重新准备这些 SQL。下表两组依次运行三轮 300 台和一轮 500 台，稳定负载窗口均为 20 秒，构建模式、数据、数据库设置、客户端节奏和管理读写相同。短时对照期间独占测试负载。

| 设备数 / 轮次 | 上线 ms（前 → 后） | 心跳往返 P95 ms（前 → 后） | 命令接收 P95 ms（前 → 后） | 管理读取循环数（前 → 后） |
| --- | ---: | ---: | ---: | ---: |
| 300 / 1 | 1,305 → 889 | 426 → 269 | 1,048 → 891 | 19 → 19 |
| 300 / 2 | 1,220 → 976 | 415 → 291 | 1,017 → 908 | 19 → 19 |
| 300 / 3 | 1,115 → 946 | 506 → 365 | 903 → 911 | 19 → 19 |
| 500 / 1 | 2,111 → 1,718 | 962 → 762 | 1,889 → 1,279 | 9 → 16 |

300 台三轮心跳 P95 的中位数降低 31.7%，命令接收 P95 的中位数降低 10.7%。第三轮的命令接收慢了 8 ms。300 台的六轮结果均满足 2,000 ms 目标。500 台单轮用于观察容量余量。

按四轮合计，核对设备和操作员权限的 SQL 在基线执行 25,740 次、规划 25,740 次，规划共用 3,990 ms。优化后执行 28,255 次、规划 27 次，规划共用 6.8 ms。座位分配查询的规划耗时从 1,886 ms 降到 2.8 ms。执行次数随设备收到回复的快慢变化。

[等待控制查询](../../crates/wccs-server/src/waiting.rs)现在按 PostgreSQL 连接准备五条固定语句，分别处理单设备授权撤销、到期、最新命令、权限和座位分配。事务每次从数据库读取当前数据。单设备退役带设备 ID 等值条件，管理列表仍处理全场。数据库重连后，新连接重新创建语句。桌面资料下载与控制轮询使用同一套当前命令校验。[连接生命周期](../../crates/wccs-server/src/database.rs)

## 资料下载与批量控制同时运行

300 个控制连接保持心跳，选取其中 16 或 300 台，从已建立的分发任务连续下载同一块 256 KiB 的合成资料。数据由 SHA-256 输出构成，客户端下载后逐块校验，遇到 HTTP 429 等待 200 ms 后重试。全部下载者取得首块后，管理员提交同一批等待命令，随后持续 30 秒读取管理接口。吞吐以已校验的有效载荷除以下载总时长。这个场景测量回环 HTTP 服务处理缓存中分块的能力；目标网络、TLS、代理和客户端落盘成本需另测。

控制查询优化后、调整下载排队前，300 台只运行控制时的命令接收 P95 为 901 ms。16 台持续下载时为 918 ms，吞吐为 57.77 MiB/s。提高至 300 台下载时，部分设备在 60 秒内始终取不到首块，测试在提交控制命令前失败。原实现名额一满就返回 429，已完成一个分块的设备可以反复抢到下一个名额。

普通分发与开赛桌面下载现在共用有界队列，仍同时处理最多 16 块。试用 2 秒等候上限时，两轮 300 台均完成，分别观察到 1,160 和 140 次 429 重试。最终选择 3 秒，同时保留低速客户端的传输时间。等候期间取消任务或轮换凭据，取得名额后仍要重新通过校验。[分发实现](../../crates/wccs-server/src/distribution.rs) · [决策记录](../decisions/0016-contest-control-and-recovery.md)

| 最终队列，按运行顺序 | 全员取得首块 ms | 有效吞吐 MiB/s | 429 重试数 | 命令接收 P95 ms |
| --- | ---: | ---: | ---: | ---: |
| 16 台下载 | 49 | 39.65 | 0 | 923 |
| 300 台下载 | 1,541 | 37.89 | 0 | 1,011 |
| 300 台下载 | 1,688 | 39.53 | 63 | 1,135 |
| 16 台下载 | 48 | 46.17 | 0 | 919 |

两轮 300 台下载都越过了原先失败的首块门槛，控制命令接收仍在 2 秒内。16 台的两轮吞吐低于原先单轮 57.77 MiB/s，尚无证据表明峰值带宽提高。本次可重复观察到的改善是全体设备都能开始下载。

## 500 客户端持续 60 分钟

2026-11-27 晚至 11-28 凌晨，500 台已注册模拟设备在 1,588 ms 内完成首轮交换。首批命令接收 P95 为 1,222 ms，最慢 1,275 ms。持续窗口内管理端完成 2,563 轮读取。全程记录 1,488,290 次常规心跳，P95 为 390 ms，最慢 1,988 ms。第 32 分钟，数据库显示 500 台均在线、500 条命令均已成功，各机最后上报时间跨度为 1 秒。结束时逐台核对了完成事件、授权到期、模拟器回到桌面和重连后没有旧命令。测试总耗时 3,608.50 秒。

首尾时段的私有内存中位数相差 5.03 MiB，采样峰值为 180.81 MiB。首轮连接完成后句柄数在 1,168～1,170 之间。仍有缓慢增长，现场复测应将负载发生器与 Linux 服务端分进程、分机采集 RSS 和队列深度，以判断增长来源。

## 300 座位管理台

Edge 158.0.4370.33 无头模式、1440 × 1000 CSS 像素，加载本机生产构建、真实登录会话和回环服务。选中含 300 名合成选手的比赛并勾选一个座位。将全部设备的最后在线时间在当前值和过期值之间交替切换，每轮连续刷新 20 次。每次检查 300 张座位卡全部切换状态、原勾选保留。从点击“立即刷新”到 DOM 更新后两个动画帧，首轮 P50 / P95 / 最大值为 100 / 128 / 142 ms，当时主机也在编译。全部构建结束后独立复测为 68 / 79 / 94 ms。两轮各等待一次页面自动轮询，从写入到观察到全员离线分别为 229 和 2,057 ms，这两个样本均包含 3 秒轮询周期的剩余时间。

## 复测入口

在仓库根目录执行，`WCCS_TEST_DATABASE_URL` 指向专用 PostgreSQL 测试数据库，连接串采用 libpq 键值格式。用例需要建表、创建 schema 和删除其测试 schema 的权限。

```powershell
$env:WCCS_LOAD_CLIENTS = '300'
$env:WCCS_LOAD_SECONDS = '20'
$env:WCCS_LOAD_DOWNLOADERS = '0'
cargo test --locked --release --target x86_64-pc-windows-msvc -p wccs-server --test http concurrent_control_preview_commit_and_reconnect -- --ignored --nocapture
```

使用 500 和 3600 运行一小时用例。持续至少 900 秒时，测试让命令在采样结束约 30 秒前到期，检查已完成回执、到期阶段、模拟桌面恢复以及重连后旧命令无法领取。较短用例验证仍有效的命令在重连时取消。测试进程用毫秒频数统计心跳 P95。本机评估的原始短测输出、SQL 统计、浏览器采样及持续负载日志位于忽略目录 `local/perf-20261127/`，该目录中的专用 PostgreSQL 实例已停止。

混合负载使用 `WCCS_LOAD_CLIENTS=300`、`WCCS_LOAD_SECONDS=30`，依次将 `WCCS_LOAD_DOWNLOADERS` 设为 0、16 或 300。每轮输出全员取得首块的耗时、有效吞吐、已校验块数、429 重试次数及控制时延。Linux 原生运行时按[容量用例说明](pre-field-hardening.md#重跑入口)提高测试进程的文件句柄上限。

## 回归与现场边界

- `pwsh -NoProfile -File scripts/check-rust.ps1` 通过固定 Windows 工具链的格式、release 构建、Clippy、107 项常规测试和 Credential Provider 构建。最终压测代码另用 8 个控制连接和 8 个下载者执行了 5 秒冒烟测试。
- 在同一专用 PostgreSQL 上执行 `cargo test --locked --release --target x86_64-pc-windows-msvc -p wccs-server --test http -- --ignored --skip concurrent_control_preview_commit_and_reconnect`，26 项通过，覆盖数据库重连后继续领取命令、设备凭据轮换、重复回执、读取名额占满时的认证与等候超时，以及等候期间撤销任务。
- `cargo check --locked -p wccs-server -p wccs-protocol --all-targets --target x86_64-unknown-linux-gnu` 使用本机 Clang、llvm-ar 和 Debian amd64 头文件交叉检查通过。`npm --prefix web run check` 的 38 项测试和生产构建通过，主 JS 包仍有 501.10 kB 的体积提示。`python -m unittest discover -s scripts/tests -v` 的 28 项回归通过。
- 目标 Linux 主机上的独立服务进程、多机房 HTTPS/WSS、客户端磁盘写入、首次注册和多管理员同时操作仍待现场验证。此次评估未部署到赛场。
